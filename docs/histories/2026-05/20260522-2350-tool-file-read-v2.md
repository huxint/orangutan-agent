### Design Intent

The token format is deliberately opaque from the agent's perspective
but structured enough to keep verification cheap. Embedding the
canonical-path SHA-256 (not the body's content hash) defeats the
accidental cross-file token replay the spec calls out without paying
the per-call SHA-256 of the file body — that cost is reserved for
high-trust paths via the future `compute_hash=true` knob. The
`(size, mtime_ns)` suffix is the cheap stat-only fingerprint
`io::compute_file_fingerprint` already returns, so the
`if_version` short-circuit costs one `stat(2)` and a SHA-256 of the
path string before we know whether to skip the body read.

The header-line envelope keeps `tool::Output` text-only — `Output v2`
is not a prerequisite. The header shape is the stable
`(path, start_line, end_line, fingerprint, bytes, truncated)` tuple
the spec acceptance criterion 9 names, so the eventual move to
`Output::structured` is a one-line callsite change. We chose a
single `\n` separator (not the literal `"\n---\n"` or similar) so the
body slice is byte-identical to the original file's range — the
agent that learned to consume `file.read v1`'s verbatim output keeps
working as long as it splits on the first newline.

Adding `ErrorKind::not_modified` to the cross-boundary enum (rather
than reusing `conflict` or `cancelled`) keeps the semantics clean:
`not_modified` is a *successful* early-out — the call did the work
the agent asked for ("tell me if anything changed since this
token"). `conflict` already means "the caller's expectation was
violated", and we still need it for the slice-46 `expected_version`
contract on `file.edit` / `file.write`. Splitting the kinds keeps
the four code paths legible: `allow` → body, `not_modified` →
no-op success, `conflict` → "your expected version is stale,
re-read", `invalid_argument` → "your input was malformed".

The byte-range test had to accept the slice-43 io contract that
`offset_bytes` is a zero-based byte skip count (the `seekg` argument
in the impl), not the 1-based "byte position" the
`range.hpp` docstring suggests. The mismatch between the docstring
and the impl is a slice-43 tech-debt item the tool layer cannot
unilaterally fix; the test pins the actual behaviour and the
spec-level alignment work stays where it lives. (The line-range
side of the schema *is* 1-based, matching the io tests.)
